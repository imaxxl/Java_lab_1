## 1. Что делает программа

Таблица профилей с загрузкой и сохранением CSV (лабораторная 1) и собственный граф, в котором эти профили
лежат (лабораторная 2): вершины — профили, рёбра — дружба с целой «силой» связи, дополнительная операция —
кратчайшая цепочка знакомств. Рядом с таблицей панель из двух вкладок показывает внутреннее устройство
структуры: граф и хеш-таблицу вершин. Долгие операции идут в фоне с индикатором и отменой.

## 3. Слои и зависимости

| Пакет | Использует |
| --- | --- |
| `gui` | `csv`, `store`, `structure`, `model` |
| `csv` | `store`, `model` |
| `store` | `structure`, `model` |
| `structure` | ничего из проекта |
| `model` | ничего из проекта |

- `structure` и `model` не импортируют другие пакеты проекта. Структура знает только про ключи и записи
  обобщённых типов, поэтому её можно проверять и с `Profile`, и с обычными числами.
- `store` склеивает модель и структуру: все правила предметной области (уникальный ID, кто может быть
  администратором, что нельзя удалять) собраны в `ProfileRepository`, а не размазаны по окнам.
- `csv` читает и пишет файлы, но данные в репозиторий не кладёт: загрузчик возвращает результат
  (`LoadResult`: профили и ошибки), а решение, что с ним делать, принимает окно.
- `gui` не хранит данные предметной области: таблица показывает снимок репозитория, а у окна из своего
  состояния только ссылка на репозиторий и флаги «есть несохранённые правки». Циклических зависимостей между
  пакетами нет.

Поток данных при загрузке файла:

```
CSV-файл ─► CsvLoader ─► LoadResult(профили, ошибки) ─► ProfileRepository.replaceAll
                                                              │ (проверка набора целиком)
                                                              ▼
таблица ◄── repository.snapshot() ◄── AdjacencyGraph ──► StructureSnapshot ─► холсты
```

## 4. Лабораторная 1: модель, проверка, CSV, окно

### 4.1 Модель

```
Profile ──┬── EditableProfile  (implements Editable)
          ├── Community        (implements Editable) + description, administratorId
          └── DeletedProfile   (final)               + reason
```

- `Profile` — базовый тип. Поля `final`, сеттеров нет: «изменить профиль» значит построить новый объект и
  заменить им старый (`ProfileRepository.replace`). Тест `ordinaryProfileCanBeReplacedWithoutMutatingOldObject`.
- Тип только для чтения (`DeletedProfile`) не реализует `Editable`. Решение «можно ли менять» принимается по
  `instanceof Editable` (кнопки окна, проверки репозитория), а не перечислением конкретных классов.
  `ProfileType.isEditableType()` нужен только для списка типов в окне «Добавить».
- Проверка значений — `Profile.validationIssues()`: id положительный, имя и город не пустые и в одной строке,
  год от 1900 до текущего. Подклассы добавляют свои правила через `super.validationIssues()`
  (у `Community`: описание, администратор положительный и не сам себе). `validate()` отдаёт только тексты.
- `ProfileType` — перечисление с подписью для интерфейса и признаком редактируемости; `ProfileType.of(profile)`
  определяет тип по классу.

### 4.2 Правила репозитория

`ProfileRepository` отвечает за то, что не может проверить сам профиль:

| Правило | Где |
| --- | --- |
| ID уникален | `validateForAdd`, `replaceAll` |
| Создавать и менять можно только `Editable` | `requireEditable` |
| При замене нельзя менять ID и тип | `validateForReplace` |
| Администратор сообщества существует и это обычный, не удалённый профиль и не сообщество | `requireAdministrator`, `canBeAdministrator` |
| Нельзя удалить профиль, который администрирует сообщество | `remove` |
| Удалённый (read-only) профиль нельзя создать через интерфейс: он попадает в набор из файла или от генератора | `replaceAll`; `forceAdd` (доступ только внутри пакета `store`) |
| Загрузка набора заменяет всё или ничего | `replaceAll` собирает новый граф, проверяет его целиком и только потом подменяет |

### 4.3 CSV

Формат профилей: UTF-8, `;`, обязательный заголовок, восемь колонок
`type;id;name;city;birthYear;description;administratorId;reason`. Позиции колонок заданы константами
`CsvFormat.TYPE … CsvFormat.REASON`. Дружбы лежат в отдельном файле `firstId;secondId;strength`.

Как загрузчик обрабатывает файл (`CsvLoader.load`):

1. Читает построчно (`BufferedReader`), проверяет заголовок; при неверном заголовке возвращает одну ошибку
   `BAD_HEADER`.
2. Каждая строка разбирается в `parseProfile`: `CsvFormat.parse` (кавычки, экранирование `""`), число полей,
   тип, обязательные колонки, числа, неиспользуемые колонки, `Profile.validationIssues()`.
3. Любая ошибка строки — это `CsvLoadException(код, номер строки, текст)`. Исключение ловится в цикле и
   складывается в список, чтение продолжается: «битые строки пропускаются».
4. После чтения проверяются связи между строками: дубликаты ID (`DUPLICATE_ID`, остаётся первая запись) и
   администраторы сообществ (`INVALID_REFERENCE`).
5. Результат — `LoadResult(profiles, errors)`; ошибки отсортированы по номеру строки.

Коды ошибок (`CsvErrorCode`): `BAD_HEADER`, `BAD_CSV_FORMAT`, `BAD_NUMBER`, `WRONG_FIELD_COUNT`, `EMPTY_FIELD`,
`UNKNOWN_TYPE`, `DUPLICATE_ID`, `DUPLICATE_FRIENDSHIP`, `INVALID_VALUE`, `INVALID_REFERENCE`.

Отмена и прогресс: загрузчик каждые 200 строк (`PROGRESS_STEP`) сообщает `LoadProgress`, а на каждой строке
проверяет `Thread.currentThread().isInterrupted()` и при отмене бросает `InterruptedIOException`.

Безопасная запись (`SafeWrite.replaceFile`): данные пишутся во временный файл в том же каталоге, затем
`Files.move` с `ATOMIC_MOVE` (если файловая система не умеет, запасной вариант с `REPLACE_EXISTING`);
временный файл удаляется в `finally`. Старый файл остаётся целым при сбое и при отмене (проверка прерывания
перед заменой). Тесты `failedMoveKeepsTargetAndCleansTemporaryFile`, `interruptedSaveKeepsOriginalFile`.

Перед сохранением `CsvSaver` прогоняет набор через `ProfileRepository.replaceAll`: невалидные данные не
попадут в файл, а вызывающий получит `IOException` с причиной.

### 4.4 Окно (первая лабораторная)

- Таблица `TableView<Profile>` (`ProfileTable`), столбцы: тип, ID, имя, город, год, дополнительно.
- Кнопки «Изменить» и «Удалить» включены, только если выбранная запись `Editable` и нет фоновой операции.
- «Добавить» открывает `ProfileEditorDialog`: поля читаются и проверяются при нажатии «Сохранить»; при ошибке
  событие гасится (`event.consume()`), окно остаётся открытым с введёнными значениями, ошибка показывается
  диалогом. Валидатор контекста (`repository::validateForAdd`) отвечает за уникальность ID и администратора.
- Заголовок окна получает «*», пока есть несохранённые изменения (`dirty`, `friendsDirty`); закрытие и
  загрузка поверх несохранённого спрашивают подтверждение (`GuiAlerts.confirmDiscard`).

## 5. Лабораторная 2: собственные структуры

### 5.1 Контракты и generics

```
EntityStore<K, T>              add, findByKey, removeByKey, size
   └── GraphStore<K, T>        + операции с Trace, replaceByKey, рёбра, цепочка, обходы, срез корзин
         ├── AdjacencyGraph<K, T>      основная реализация
         └── SynchronizedGraph<K, T>   обёртка над любым GraphStore
HashStore<K, T> implements EntityStore<K, T>      индекс вершин внутри AdjacencyGraph
```

`K` — тип ключа, `T` — тип записи. Ключ вычисляет `KeyExtractor<K, T>` (`Profile::getId`), обходы принимают
`Visitor<T>` и `EdgeVisitor<K>`. Это собственные интерфейсы вместо `java.util.function`, чтобы пакет
`structure` вообще не касался `java.util`; охранный тест читает исходники пакета и ищет `java.util`.

Массив обобщённого типа создать нельзя, поэтому в `HashStore.newTable`, в очереди обхода и в `Chain`
используется приведение внутри класса; оно сосредоточено в нескольких методах с `@SuppressWarnings("unchecked")`.

### 5.2 `HashStore`: хеш-таблица с цепочками

Устройство:

- массив корзин `Node<K, T>[] buckets`; каждый узел хранит ключ, хеш, значение и ссылку `next` на следующий
  узел той же корзины;
- длина массива всегда степень двойки (`tableSize`), номер корзины `hash & (length - 1)`;
- хеш = `h ^ (h >>> 16)`, где `h = key.hashCode()`: старшие биты подмешиваются в младшие, иначе при малой длине
  массива они бы не участвовали в выборе корзины;
- коэффициент заполнения 3/4: при `size > length * 3 / 4` массив удваивается (`resize`), узлы
  перекладываются по новым корзинам без создания новых объектов;
- кроме цепочек, узлы связаны двусвязным списком в порядке добавления (`before`, `after`, `first`, `last`):
  он даёт обход в порядке загрузки и удаление узла из списка за O(1).

Вставка целиком:

```java
public void add(T entity, Trace trace) {
    if (entity == null) throw new IllegalArgumentException("Пустую запись добавить нельзя");
    K key = keys.keyOf(entity);
    int hash = hash(key);
    int index = indexFor(hash, buckets.length);
    for (Node<K, T> node = buckets[index]; node != null; node = node.next) {
        if (trace != null) trace.visit(node.key);
        if (node.hash == hash && node.key.equals(key)) {
            throw new IllegalArgumentException("Ключ уже существует: " + key);
        }
    }
    Node<K, T> created = new Node<>(key, hash, entity);
    created.next = buckets[index];
    buckets[index] = created;
    linkLast(created);
    size++;
    if (trace != null) trace.markResult(key);
    if (autoResize && size > threshold()) resize();
}
```

Построчно: проверка пустой записи → ключ → хеш → корзина → просмотр цепочки на дубликат (каждый просмотренный
узел записывается в `Trace`, именно он потом подсвечивается) → новый узел вставляется в голову цепочки
(O(1)) → добавляется в список порядка → счётчик → при переполнении удвоение. Сравнение сначала по `hash`, и
только при совпадении по `equals`: дешевле, чем `equals` для каждого узла.

Поиск и удаление идут тем же путём по цепочке; при удалении запоминается предыдущий узел, чтобы «перешить»
`next`, и узел снимается из списка порядка. `replaceByKey` подменяет значение в найденном узле, ключ и
позиция не меняются.

Параметры `capacity` и `autoResize` в конструкторе нужны тестам и опыту с гонкой: таблица фиксированной
длины делает цепочки длинными и коллизии заметными.

### 5.3 `AdjacencyGraph`: граф со списками смежности

```
vertices : HashStore<K, Vertex>            индекс «ключ → вершина»

Vertex { key, sequence, value, edges, degree, mark, parent }
   edges ─► Edge { to, strength, next } ─► Edge ─► …      односвязный список соседей
```

- Ребро неориентированное и хранится двумя узлами `Edge` — по одному в списке каждой вершины. Поэтому
  соседей любой вершины можно перечислить просто обходом её списка, а у ребра одна сила на оба узла.
- `degree` — длина списка, `edgeCount` — число рёбер (каждое считается один раз).
- `sequence` — порядковый номер вершины. `forEachEdge` отдаёт ребро только из вершины с меньшим номером:
  каждое ребро выдаётся ровно один раз, хотя узлов два.
- `mark` и `parent` нужны обходу в ширину и хранятся прямо в вершине.

Добавление ребра проверяет силу (≥ 1), «не сам с собой», существование обеих вершин и дубликат; повтор ищется
в списке той вершины, у которой меньше соседей (`min(deg a, deg b)`), поэтому связь с «хабом» (вершиной
с очень многими соседями) остаётся дешёвой. Затем два узла вставляются в головы обоих списков.

Удаление вершины — самое тонкое место:

```java
public boolean removeByKey(K key, Trace trace) {
    Vertex<K, T> vertex = vertices.findByKey(key, null);
    if (vertex == null) return false;
    for (Edge<K, T> edge = vertex.edges; edge != null; edge = edge.next) {
        unlink(edge.to, vertex);
        edgeCount--;
    }
    vertex.edges = null;
    vertex.degree = 0;
    return vertices.removeByKey(key, trace);
}
```

Сначала у каждого соседа снимается узел, указывающий на удаляемую вершину (списки односвязные, поэтому
`unlink` ищет узел проходом по списку соседа), потом вершина удаляется из индекса. «Висячих» рёбер не остаётся:
тест `removingVertexRemovesItsEdgesFromNeighbours`. Цена — сумма степеней соседей, а не просто степень.

### 5.4 Поиск цепочки знакомств

```java
nextStamp();
Object[] queue = new Object[vertices.size()];
int head = 0;
int tail = 0;
start.mark = stamp;
start.parent = null;
queue[tail++] = start;
while (head < tail) {
    Vertex<K, T> current = (Vertex<K, T>) queue[head++];
    if (trace != null) trace.visit(current.key);
    if (current == goal) break;
    for (Edge<K, T> edge = current.edges; edge != null; edge = edge.next) {
        Vertex<K, T> next = edge.to;
        if (next.mark != stamp) {
            next.mark = stamp;
            next.parent = current;
            queue[tail++] = next;
        }
    }
}
if (goal.mark != stamp) return Chain.none();
```

- Обход в ширину находит путь с наименьшим числом связей. Сила связи в длину пути не входит (нужна была бы
  Дейкстра), тест `chainIsShortestByLinksNotByStrength`.
- Очередь — массив длиной в число вершин: каждая вершина попадает в неё не больше одного раза, значит места хватит.
  `head` и `tail` — индексы, ничего не сдвигается.
- «Посещена» хранится в вершине: `mark == stamp`. Перед каждым обходом `stamp` увеличивается, поэтому метки не
  нужно очищать. При переполнении `stamp` метки обнуляются (`nextStamp`; тест
  `repeatedSearchesDoNotInterfereAndSurviveStampOverflow`).
- `parent` указывает, откуда пришли; путь восстанавливается от цели к началу (`restorePath`) и возвращается как
  `Chain` (ключи от начала к цели). Цепочка из одной вершины — когда начало совпадает с целью, пустая — когда
  пути нет или вершины не существует.
- Обход записывает в `Trace` каждую вершину, взятую из очереди: по ней панель подсвечивает «посещённые».
- Обход пишет в вершины (`mark`, `parent`), поэтому даже «читающая» операция небезопасна при параллельном
  вызове — см. раздел 7.

### 5.5 Асимптотика

`V` — число вершин, `E` — число рёбер, `deg` — число соседей вершины.

| Операция | Сложность | Обоснование |
| --- | --- | --- |
| Вставка вершины | O(1) в среднем | хеш, вставка в голову цепочки; удвоение массива даёт амортизированно O(1); если все ключи в одной корзине — O(n) |
| Поиск вершины | O(1) в среднем | одна цепочка; при одинаковых хешах — O(n) |
| Замена записи | O(1) в среднем | поиск узла и подмена ссылки, рёбра не трогаются |
| Удаление вершины | O(1 + Σ deg(u)) по соседям u | у каждого соседа ищется и снимается один узел |
| Добавление связи | O(min(deg a, deg b)) | дубликат ищется в более коротком списке, вставка в голову — O(1) |
| Удаление связи | O(deg a + deg b) | узел ищется и снимается в обоих списках |
| Сила связи | O(min(deg a, deg b)) | поиск в более коротком списке |
| Цепочка знакомств | O(V + E) | каждая вершина в очереди один раз, каждый узел списка просматривается один раз |
| Обход вершин | O(n) | двусвязный список порядка добавления |

В репозитории `remove` добавляет O(V): перед удалением просматриваются все вершины, чтобы выяснить, не
администрирует ли профиль какое-либо сообщество.

### 5.6 След операции и подсветка

`Trace` — массив ключей с `visit(key)` (растёт удвоением) и `markResult(key)`. Он необязательный параметр
операций (`null` — не записывать), поэтому операция одна и та же с визуализацией и без. Подсвечивается то,
что структура действительно просмотрела, а не результат отдельной «имитации».

## 6. Визуализация, генерация, фон

### 6.1 Как рисуется панель

```
операция(trace) ─► Highlight.of(trace, chain, focus, подпись)
                         │
repository.structure(40, 32, 8) ─► StructureSnapshot
                         ▼
StructureView.show(repository, highlight) ─► GraphPainter.paint + HashPainter.paint
```

- `ProfileRepository.structure` под замком делает неизменяемый `StructureSnapshot`: первые `MAX_VERTICES = 40`
  вершин, рёбра между ними, первые `MAX_BUCKETS = 32` корзин по `MAX_CHAIN = 8` узлов; общие числа хранятся
  отдельно и выводятся текстом. Рисование поэтому не зависит от размера данных и не трогает живые узлы.
- `Highlight` — запись: посещённые ключи (с порядком посещения), путь, ключ в фокусе, подпись.
- Перерисовка полная: каждый раз заливается фон и рисуется всё заново, в том числе при изменении размера
  (`StructureView` слушает ширину и высоту холстов). Цвета: тип записи — заливка, посещённая вершина — жёлтая,
  путь — красные рёбра и обводка, найденный элемент — зелёное кольцо.
- Вкладка «Граф»: вершины по кругу, сила связи на рёбрах (если рёбер не больше 30). Вкладка «Хеш-таблица»:
  корзины в два столбца, цепочки прямоугольников.
- Рисующие классы — только статические методы от `GraphicsContext` и данных, без состояния; это позволяет
  проверять цвета пикселей в `StructurePaintingTest`.

### 6.2 Генерация

`DataGenerator.generate(repository, count, listener, cancelled)`:

- нумерация продолжается после `repository.maxId()`, существующие данные не трогаются;
- тип выбирается броском 0–99: 8 % сообществ (если уже есть кому быть администратором), 4 % удалённых, остальные
  обычные;
- у каждого нового профиля до трёх дружб со случайными уже существующими (в том числе созданными в этом же
  запуске), сила 1–10;
- генератор получает `seed`: при одинаковых зерне и исходных данных получается один и тот же набор
  (`sameSeedGivesSameData`); окно подставляет `System.nanoTime()`;
- прогресс — `listener.progress(done, total)`, отмена — опрос `cancelled`; при отмене созданное удаляется с
  конца (`rollback`), чтобы сообщество исчезало раньше своего администратора. Откат точный
  (`cancellationRollsEverythingBack`).

### 6.3 Фоновые задачи (`TaskRunner`)

```
поток JavaFX ──run(task)──► busy = true, кнопки заблокированы, ProgressBar связан с task.progressProperty()
                                 │
                                 ▼
            поток «csv-io» (один, демон):   task.call()  — чтение / запись / генерация
                                 │
                                 ▼
поток JavaFX ◄── setOnSucceeded / setOnFailed ── finish(): busy = false, обработчик результата
```

- Исполнитель — один поток: две долгие операции одновременно запретить проще, чем синхронизировать
  (`run` бросает `IllegalStateException`, если уже занято; кнопки при этом и так заблокированы).
- Всё, что меняет интерфейс, выполняется в обработчиках `setOnSucceeded` / `setOnFailed`, то есть в потоке JavaFX.
  Фоновый код работает только с репозиторием и файлами.
- Отмена: `cancel()` ставит флаг `cancelRequested` и вызывает `interrupt()` у рабочего потока. Файловые
  операции проверяют прерывание и бросают `InterruptedIOException`, генератор опрашивает флаг. Если задача
  упала с `InterruptedIOException` при поднятом флаге — это отмена, а не ошибка: показывается «Операция отменена».

```java
executor.execute(() -> {
    if (cancelRequested) Thread.currentThread().interrupt();
    task.run();
});
```

Этот фрагмент нужен потому, что `ThreadPoolExecutor` сбрасывает флаг прерывания перед запуском задачи: отмена,
пришедшая до старта, иначе бы потерялась.

- `cancelRequested` и `worker` объявлены `volatile`: пишет поток интерфейса, читает рабочий поток.
- При закрытии окна во время операции окно не закрывается и показывается сообщение; `stop()` останавливает
  исполнитель.
- Отмена загрузки дружб и генерации откатывает уже добавленное: данные не остаются в промежуточном состоянии
  (`OperationsPanel.apply`, `DataGenerator.rollback`).
- Блокировка потока интерфейса больше 100 мс недопустима, поэтому в нём остаются только быстрые вещи:
  обновление таблицы (30–75 мс на 10⁵ записей), рисование среза, поиск (O(1)) и цепочка (около 13 мс на 10⁵).

## 7. Потоки и защита от гонки

Опыт (`RaceExperiment.run(guarded, threads, perThread)`): несколько потоков одновременно добавляют вершины с
разными ключами, затем рёбра от общей вершины. В конце сравниваются ожидаемые числа, значения счётчиков и
пересчёт обходом (`countVertices` по корзинам, `countNeighbors` по списку смежности).

Без защиты поток читает поле, другой его меняет, первый записывает старое значение: часть вставок и приращений
счётчика теряется; иногда ребро не добавляется, потому что вершина «потерялась» — это исключение считается как
сбой. Из записи опыта (4 потока по 20 000 вставок): счётчик вершин 71 556–78 124 вместо 80 001. Под защитой числа
совпадают точно.

Защита:

- `SynchronizedGraph` — обёртка (декоратор) над любым `GraphStore`: каждый метод `synchronized`, обходы
  выполняются внутри замка. Один и тот же `AdjacencyGraph` можно использовать без защиты (в опыте) и с защитой
  (в репозитории).
- `ProfileRepository` тоже синхронизирован: составная операция «проверить правила и добавить» должна быть
  атомарной, а замок обёртки защищает только один вызов. Порядок захвата всегда «репозиторий → граф», граф
  репозиторий не вызывает: взаимной блокировки быть не может.
- Обход в ширину пишет метки в вершины, поэтому его тоже нужно защищать как запись.
- Таблице отдаётся неизменяемый `snapshot()`, сделанный под замком.
- Накладные расходы замка в одном потоке — от нуля до 45 % на коротких операциях (таблица в разделе 8).

## 9. Вероятные вопросы и краткие ответы

**Какие типы записей и как это связано с `Editable`?** Базовый тип — `Profile` (его обычная редактируемая
разновидность — `EditableProfile`), только для чтения — `DeletedProfile`, редактируемый с дополнительными
полями — `Community`. Кнопка «Изменить» включена, только если выбранный объект `instanceof Editable`.

**Как пропускаются битые строки?** Разбор одной строки бросает `CsvLoadException`, цикл загрузки ловит его,
добавляет в список ошибок и идёт дальше; пользователь видит номер строки, код и сообщение.

**Зачем временный файл при сохранении?** Чтобы сбой или отмена посреди записи не испортили прежний файл:
пишем рядом, потом атомарно заменяем.

**Почему репозиторий проверяет правила, а не окно?** Одни и те же правила нужны окну, загрузке из файла,
генератору и тестам; в одном месте их проще проверять и они не расходятся.

**Почему хеш-таблица, а не дерево?** Нужен поиск по ID, порядок по ключу не нужен; в среднем O(1) против
O(log n). Порядок добавления даёт отдельный двусвязный список.

**Что такое коллизия и что с ней делает ваша таблица?** Разные ключи в одной корзине; она хранит цепочку
узлов, поиск сравнивает хеш, потом `equals`. Хорошо видно на вкладке «Хеш-таблица»: пока корзин 16, ключи 1, 17
и 33 лежат в корзине [1].

**Зачем сначала сравнивать `hash`, а потом `equals`?** Сравнение целых дешевле, `equals` вызывается только
при совпадении хешей.

**Почему размер массива — степень двойки?** Номер корзины получается побитовым «и», без деления; при удвоении
узел остаётся в той же или в «парной» корзине.

**Почему списки смежности, а не матрица?** Матрица для 10⁵ вершин — 10¹⁰ ячеек; списки занимают O(V + E).

**Почему ребро хранится дважды и чем это плохо?** Так проще перечислять соседей и искать путь. Минус — при
удалении вершины надо чистить списки всех соседей, поэтому удаление O(1 + Σ deg).

**Как обход в ширину не зацикливается?** Каждая вершина получает метку `mark = stamp` при попадании в очередь и
второй раз туда не попадает.

**Зачем `stamp`?** Чтобы не очищать метки перед каждым обходом: достаточно увеличить счётчик.

**Почему очередь — `Object[]`?** Нельзя создать массив обобщённого типа; приведение безопасно, потому что
кладутся только вершины этого же графа.

**Где в проекте используется `java.util`?** В пакете `structure` нигде (проверяет тест). Вне структуры:
результат разбора CSV, `Map` и `Set` для проверки дубликатов при загрузке, снимок для таблицы (`TableView`
работает с `ObservableList`), `Random` в генераторе. Основное хранилище — собственный граф.

**Как рисуется структура и почему показываются только 40 вершин?** Репозиторий делает неизменяемый срез;
операции пишут посещённые узлы в `Trace`; из него строится `Highlight`; панель очищается и рисуется заново.
Больше 40 вершин в круге нечитаемы, общие числа показаны текстом.

**Как устроены фоновые задачи и отмена?** `TaskRunner` запускает `Task` на отдельном потоке, связывает
индикатор, блокирует кнопки; обновление интерфейса — в обработчиках результата в потоке JavaFX. Отмена —
флаг плюс `interrupt()`; файловые операции реагируют на прерывание, генератор опрашивает флаг и откатывает.

**Что такое гонка и как вы её показали?** Несколько потоков меняют общие поля без блокировок, часть записей
теряется. В `RaceDialog` без защиты ожидаемое и фактическое число расходятся, под `synchronized` — совпадают.

**Почему мало одного `synchronized` в `SynchronizedGraph`?** Он делает атомарным один вызов. «Проверить и
добавить» — два вызова, поэтому `ProfileRepository` синхронизирован сам.

**Может ли быть взаимная блокировка?** Нет: замки всегда берутся в порядке «репозиторий → граф», обратного
вызова нет.

**Зачем `volatile`?** Чтобы запись флага в одном потоке была видна в другом.

**Почему `Task`, а не просто `Thread`?** `Task` даёт прогресс, состояние и обработчики результата в потоке
JavaFX.

**Как проверяли корректность структур?** Случайные операции сверяются с `HashMap` и с обходом на
стандартных коллекциях; тест на отсутствие `java.util`; тест на удаление рёбер; замеры сверяют, что обе
реализации находят цепочки одинаковой длины.

## 10. Известные ограничения

- Панель показывает срез из 40 вершин и 32 корзин; граф большего размера целиком не рисуется.
- Дружбы хранятся отдельным файлом; загрузка нового набора профилей создаёт новый граф и сбрасывает
  дружбы, их загружают отдельно.
- Сила уже существующей связи не меняется: чтобы изменить, связь удаляют и добавляют заново.
- `Profile` не абстрактный: базовый тип можно создать напрямую (так делают тесты и замеры), но репозиторий
  отвергает всё, что не `Editable`, при добавлении через интерфейс.
- Удаление профиля в репозитории просматривает все вершины (проверка администраторов), O(V).
- Замеры сняты на одной машине с двумя ядрами; сборка проверялась на Linux.
- Многострочные поля CSV не поддерживаются: разбор построчный, переводы строк в полях запрещены при вводе.
